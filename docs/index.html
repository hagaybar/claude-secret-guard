🛡 secret-guard — how it decides

A map of the mod's logic (hooks/register.tsx + hooks/rules.ts), for reading without reading the code. Source and install: github.com/hagaybar/claude-secret-guard
First draft. Pattern-based and best effort: it catches the shapes it knows, not every possible leak.

1 · Three moments the guard acts

Session start
Reads the environment once; keeps values of variables whose names look secret (…_KEY, …_TOKEN, …SECRET…, …PASSWORD…, …AUTH…), 8+ chars, not paths. In memory only. Registers /guard, sets the status line.
Before every tool call
Inspects what the call would do. Finds a risk → block (or flag in warn mode). No risk → run.
Before every row is stored
Scans text going into the transcript (tool output, replies, prompts). Replaces known values and token-shaped strings with [redacted:NAME].

4 · Token shapes it recognises

AWS access key · GitHub token / fine-grained PAT · Anthropic key · OpenAI-style key · Slack token · Google API key · Ex Libris (Alma) API key · PEM private key header · JWT · password = "…"-style hard-coded credentials (checked, not redacted).

6 · Known gaps (why it's a first draft)

  • Commands in a form the patterns don't anticipate (aliases, scripts, eval, odd quoting) can pass.
  • Only variables present at session start, with secret-looking names, are known by value.
  • Git checks run in the session folder (or a leading cd / git -C); a commit chained after git add in one command is checked against what was staged before it.
  • Redaction can't reach anything already stored, committed or pushed.
